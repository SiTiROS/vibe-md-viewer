## Стек и почему он такой

| Решение | Почему |
| --- | --- |
| **Rust** | Скорость машинного кода без рантайма + защита от ошибок памяти в самом рискованном коде (разбор чужих `.md`, конвертеры, потоки). |
| **Win32 + RichEdit** (`msftedit.dll`) | Компонент встроен в Windows: форматированный текст, таблицы, картинки, правка, отмена. Старт окна — десятки миллисекунд. |
| Без WebView2/Edge/Electron | WebView2 — это движок Edge (пользователь хочет его удалить), а на старте он в разы медленнее нативного окна. Браузерный движок — ещё и основная поверхность атак у markdown-программ (см. [SECURITY.ru.md](SECURITY.ru.md)). |
| **pulldown-cmark** | Быстрый, проверенный (используется в rustdoc/mdBook) разборщик CommonMark + GFM. Отдаёт диапазоны в исходнике — на них построена подсветка редактора. |
| **image** (только Rust-декодеры) | PNG/JPEG/GIF/BMP/WebP/ICO декодируются безопасным Rust-кодом с лимитами. Системные кодеки Windows чужие байты не видят. |
| Статический CRT, CFG | exe не требует VC++ Redistributable; Control Flow Guard включён флагом компилятора. |

Альтернативы и их замеры/оценки обсуждались при выборе стека (C++ Win32, C# WPF/WinForms/Avalonia, WebView2, Electron) — итог: Rust + RichEdit даёт ту же скорость, что C++, при более сильных гарантиях безопасности.

## Путь от двойного щелчка до картинки на экране

1. `security::harden_process()` — политика загрузки DLL.
2. Загрузка `msftedit.dll` из System32, создание окна и двух RichEdit-контролов (просмотр — только чтение; редактор — скрыт до первого перехода в режим правки).
3. `doc::load` — чтение файла (лимит 64 МБ), определение кодировки, нормализация переводов строк.
4. `render::render` — один проход pulldown-cmark → строка RTF. Весь текст документа экранируется.
5. **Загрузка по частям** (см. ниже): `EM_SETTEXTEX` получает только часть RTF с нужным местом документа, окно показывается и рисуется (на этом замеряется время запуска), остальные части догружаются в фоне.
6. Картинки: для каждой — проверка политики (`images::resolve`), затем задача в пул потоков. Потоки создаются лениво: документ без картинок за них не платит.
7. Готовая картинка (уже уменьшенная под ширину колонки и перекодированная) вставляется точно на место скрытого маркера через TOM `ITextRange2::SetText2(tomConvertRTF)`.

## Загрузка по частям

RichEdit разбирает RTF медленно — около 0,5 мкс на байт (документ на 275 КБ с сотнями блоков кода = 1 МБ RTF ≈ 500 мс), причём тот же текст без оформления грузится за 50 мс: дорог сам разборщик, ускорить его нельзя. Поэтому:

- `render` отмечает границы частей (~40 КБ RTF) — только между обычными абзацами верхнего уровня, когда всё закрыто (не внутри таблиц, цитат, групп), так что каждая часть — цельный RTF (`Rendered::splits`, вместе со смещением в исходнике);
- `render_view` грузит часть с нужным местом (`Anchor`: смещение части в исходнике + номер символа + положение на экране) и ещё столько, чтобы под ним было два экрана; остальное — по одной части на таймер `T_LOAD` (WM_TIMER приходит, только когда нет ввода и отрисовки — окно отзывчиво);
- части выше экрана вставляются в начало с компенсацией прокрутки (место чтения не дёргается), ниже — в конец; вставка через TOM `SetText2(tomConvertRTF)` не трогает выделение;
- при полной замене текста RichEdit «съедает» последний `\par` (он сливается с конечным абзацем), при вставке через TOM — нет; поэтому только первой загружаемой части добавляется пустой крошечный абзац (тест `chunked_load_equals_full_load`: документ, собранный частями от середины, совпадает с загруженным целиком символ в символ);
- поиск, переход к разделу, Ctrl+A, Home/End, снимок и самотест сначала догружают всё (`finish_loading`); картинки и подписи из незагруженных частей ждут в `pending_*`.

Смена темы, ширины, масштаба, правка в режиме «Код» перерисовывают документ «на том же месте» (`view_anchor`). Замер (`scripts\profile.ps1`, 275 КБ): открытие — 60 мс до показа + 110 мс в фоне (было 520 мс одним куском), смена темы — 75 мс (было 540).

## Служебные маркеры в режиме просмотра

RichEdit не умеет «привязывать данные к тексту», поэтому рендер вставляет **скрытые** (`\v`) символы из Private Use Area:

| Символы | Значение |
| --- | --- |
| `U+E000 + id` … `U+F8FE` | начало/конец ссылки `id` |
| `U+E800 + id` | якорь заголовка `id` (для `#раздел`) |
| `U+EC00 + id` … `U+F8FD` | место картинки `id`; между маркерами — скрытая подпись `[🖼 alt]`, которая открывается, если картинку показать нельзя |
| `U+202F` … `U+202F` | видимые узкие неразрывные пробелы-поля по краям `кода` в тексте — по ним просмотр рисует подложку; неразрывные, чтобы плашка переносилась на новую строку целиком (такие пробелы из документа заменяются на тонкий `U+2009` той же ширины) |

После загрузки текст контрола читается с `GT_RAWTEXT` (позиции символов совпадают с внутренними, включая служебные символы таблиц) и строится индекс позиций. Наведение и клик → `EM_CHARFROMPOS` → поиск ссылки по индексу → политика `links::classify`.

Такие же символы из самого документа заменяются на `U+FFFD`, поэтому подделать маркер нельзя.

Почему не поля `HYPERLINK` RichEdit: ими нельзя управлять так же строго, а обработку ссылок мы целиком держим у себя.

## Оформление, которого RichEdit не умеет

RichEdit не рисует рамки абзацев, поэтому:

- полоса слева у цитаты — однострочная таблица с левой рамкой ячейки (по строке на абзац, вместе они выглядят сплошной полосой);
- линия под H1/H2 и горизонтальная линия — таблица с нижней/верхней рамкой;
- блок кода — таблица из одной ячейки с фоном (`\clcbpat`) и полями, без рамки; цвета подсветки — группы `\cfN` (индексы 12–18 таблицы цветов);
- серая сетка ячеек отключена стилем `SES_HIDEGRIDLINES`.

Грабли RichEdit, найденные замерами (тесты в `render.rs`):

- **Тёмная заливка ячейки съедает цвета текста.** Если яркость `\clcbpat` ниже ~20% (замерено: `46,52,60` — цвета есть, `44,50,58` — нет), RichEdit рисует весь текст ячейки одним цветом, «обратным» фону. Поэтому фон блоков кода в тёмной теме — `47,54,64`; тест `dark_code_block_keeps_syntax_colors` рисует блок настоящим RichEdit и ищет пиксели цвета ключевых слов. На фон символов (`\highlight`) это не распространяется.
- **Фон символов (`\highlight`) заливает всю высоту строки** при любом межстрочном интервале и вместе с отступом `\sb` абзаца — плашки `кода` на соседних строках сливались в блок. Поэтому подложку `кода` в просмотре рисует сам просмотр (`paint_chips`): после отрисовки RichEdit, только в обновлённой области (иначе наложилась бы дважды), полупрозрачным прямоугольником по высоте шрифта от базовой линии (TOM `GetPoint(TA_BASELINE)`), со скруглёнными углами; текст под ней почти не меняет цвет. Запрос положения у RichEdit стоит ~50 мкс, поэтому геометрия плашки считается один раз и хранится в координатах документа (`chip_geo`): на кадре прокрутки её достаточно сдвинуть. Кеш сбрасывается при смене текста, полей, масштаба, длины текста, высоты документа и при показе подписи картинки; самотест сравнивает картинку после прокрутки кадрами с полной перерисовкой. В редакторах — по-прежнему `\highlight` (`code_inline_bg`).
- **Поля `EM_SETRECT` сверху/снизу при прокрутке не перерисовываются** — в них оставались полоски чужого текста. В просмотре отступы сверху и место после конца — абзацами в самом документе; в редакторе полосы полей перерисовываются при каждом изменении прокрутки (`fix_margin_strips`).
- **`EM_SETRECT` с теми же полями всё равно переносит весь текст** — на большом документе десятки мс при каждом переключении режима. `set_margins` пропускает вызов, если поля не изменились.
- **Масштаб (`EM_SETZOOM`) умножает и поля** — `EM_SETRECT`/`EM_SETMARGINS` задают поля «до масштаба». При масштабе < 100% нужные поля бывают шире самого окна: `EM_SETRECT` такой прямоугольник отвергает (сбрасывает поля), `EM_SETMARGINS` принимает. Поэтому левое/правое поле — `EM_SETMARGINS`, верх/низ — `EM_SETRECT`.
- **Таблица не бывает шире 22 дюймов** (31680 twips = 2112 px при 96 dpi и 100%): `\cellx` правее молча обрезается. Блоки кода, линии и цитаты — таблицы, поэтому колонка текста не шире этого предела (см. «Ширина колонки»).
- **Полоса прокрутки появляется только у длинного документа** и сужает текст, а таблицы остаются прежней ширины — у просмотра и редактора она всегда есть (`ES_DISABLENOSCROLL`).
- **Замена всего текста (`EM_SETTEXTEX`) сбрасывает масштаб на 100%** — после неё масштаб возвращается из настроек. Ширина таблиц и блоков кода считается с учётом масштаба, иначе при масштабе ≠ 100% они были уже или шире текста.
- **`SB_BOTTOM` не доводит до конца большого документа** — Home/End и колесо прокручивают сами по пикселям (`EM_SETSCROLLPOS`, 32-битные координаты проверены на документе в 196 000 px).
- **Пробел в Consolas — шириной в целый символ**, в том числе тонкий (U+2009). Поля плашки `кода` набираются узким пробелом шрифтом Segoe UI.
- **Невидимые символы-«склейки» (U+2060) RichEdit рисует точкой** — запрет переноса делается неразрывным пробелом.

Тест `richedit_layout_assumptions` проверяет на настоящем RichEdit поля при масштабе 50/100/150% и предел ширины таблицы.

## Ширина колонки

Колонку считает одна функция `App::column` — и поля RichEdit, и ширину таблиц/картинок для рендера, поэтому правый край текста, блоков кода и линий совпадает (самотест проверяет по пикселям: исходное окно, окно шире на 13 px, масштаб 150% и 50%, другой режим колонки).

- `settings.wide` (по умолчанию `true`): поля по 3% ширины окна (не меньше 28 px); иначе — колонка 900 px (× масштаб) по центру.
- Колонка не шире 22 дюймов × масштаб (предел таблиц RichEdit): на большом мониторе лишнее место — поровну по бокам. 2560 px при 100% → колонка 2112 px.
- Поля считаются в экранных px и делятся на масштаб (RichEdit умножит их обратно).
- Любое изменение ширины (даже на 1 px) — перерисовка через 160 мс после изменения окна (`T_RESIZE`).
- Развёрнутое окно: пока оно скрыто, ему сразу ставится размер развёрнутого (`presize_maximized`) — документ рисуется один раз и под нужную ширину.

Первое окно без сохранённого положения — 85×88% рабочей области по центру.

## Прокрутка, выделение, масштаб

- Колесо, стрелки, PgUp/PgDn, пробел — плавная прокрутка: цель копится, положение приближается к ней экспоненциально (~60 мс, по прошедшему времени). Кадры ведёт цикл сообщений: пока идёт прокрутка, он разбирает накопившиеся сообщения, делает шаг (`EM_SETSCROLLPOS` + `UpdateWindow`) и ждёт следующего кадра экрана (`DwmFlush`) — шагов столько, сколько герц у монитора (60/144/…), и они равномерные. Таймер Windows (шаг ~15,6 мс) давал ~60 неровных кадров — на 144 Гц это выглядело «мало fps». Таймер `T_SMOOTH` (30 мс) остался страховкой для модальных циклов (меню, перетаскивание окна). Кадр на 2560×1380: в среднем 2,6 мс, 95% — до 3,6 мс (бюджет при 144 Гц — 6,9 мс). Сенсорные панели с мелкими шагами работают так же.
- Ctrl+колесо — масштаб (шаги копятся до «щелчка»), кнопки `−  100%  +` на панели.
- Выделение протягиванием в просмотре делаем сами (`WM_LBUTTONDOWN`/`WM_MOUSEMOVE`/`WM_LBUTTONUP`, за краем окна — прокрутка): RichEdit «только для чтения» его не делал. Фокус RichEdit получает, а мигающий курсор прячется `HideCaret` после каждого сообщения. Двойной щелчок (слово) — штатный RichEdit. Щелчок без протягивания по ссылке — переход.

## Автосохранение

Как в IDE: через 1,2 с после паузы в наборе (`T_AUTOSAVE`), при переходе в просмотр, при уходе из окна и при закрытии/переходе к другому файлу — без вопросов. Тихо: ошибка записи — в строке состояния, без окна. Запись — та же атомарная (`doc::save`). Выключается `autosave=0` в `settings.ini` (тогда вернётся кнопка «Сохранить» и вопрос при закрытии).

## Язык интерфейса

Английский (по умолчанию) и русский. Строки лежат прямо в коде парами: `tr!("English", "Русский")` → `&str`, `trf!("Saved {n}", "Сохранено {n}")` → `String` (подстановки по именам — порядок слов в языках может различаться). Язык — общий флаг процесса (`i18n::set`), выбирается до первого окна: из `lang=` в своих `settings.ini`, а у скачанного установщика — из настроек установленной программы (`settings::initial_lang`). Кнопка **EN / RU** на панели переключает язык сразу: панели, плашки, строка состояния, стартовая страница (`assets/welcome.en.md` / `welcome.ru.md`). Комментарии в коде, сообщения тестов и самотеста — на английском.

## Режимы редактирования

В редакторе всегда находится **сам markdown**: сохранение без потерь, без обратной конвертации.

- После каждой правки (сообщение `EN_CHANGE` → отложенный `WM_APP_RESTYLE`) текст заново разбирается `styler::analyze` (pulldown-cmark с диапазонами) в разбиение на прогоны с битовыми флагами (`STRONG`, `MARKER`, `LINK`, `URL`, уровень заголовка…).
- `editor::Styler` сравнивает новые прогоны со старыми (общий префикс/суффикс текста) и применяет через TOM только изменившиеся. Изменения оформления не попадают в историю отмены (`tomSuspend`), отрисовка заморожена (`Freeze`).
- «Визуальный»: пропорциональный шрифт, заголовки крупные, маркеры (`**`, `#`, `](url)`, `> `) скрыты везде, кроме строки с курсором; маркеры неупорядоченных списков заменены настоящими маркерами абзаца.
- «Код»: моноширинный шрифт, всё видно, разметка приглушена; справа предпросмотр, перерисовывается через 350 мс после паузы в наборе, прокрутка синхронизирована.
- Подсветка синтаксиса в обоих режимах: `styler` кладёт вид лексемы (`highlight::Kind`) в биты 26–28 флагов (`fl::SYN_MASK`) внутри тела блока кода, `editor` выбирает по ним цвет темы (`syn_*`), комментарии — курсивом.
- «Изменён» = хеш текста редактора ≠ хеш загруженного/сохранённого текста (отмена до исходного снимает пометку).

## Установка и обновление (`install.rs`)

Один и тот же exe — и программа, и установщик. Установка как у обычного софта.

| Область | Папка | Реестр | Права |
| --- | --- | --- | --- |
| **Для всех (по умолчанию)** | только `%ProgramFiles%\vibe-md-viewer` (`SHGetKnownFolderPath(FOLDERID_ProgramFiles)`), своя папка — нельзя | HKLM | UAC — только на время операции |
| Для себя (нет прав администратора / отказ в UAC) | `%LOCALAPPDATA%\Programs\vibe-md-viewer` | HKCU | обычные |

Повышение прав: обычная копия запускает **саму себя** через `ShellExecuteExW(verb="runas")` с параметрами `--elevated install|update|uninstall --target "<папка>"` и ждёт код возврата. Повышенная копия ничего не спрашивает, только делает операцию (`elevated_main`). Окно «Чем открыть» и запуск обновлённой программы — всегда из **обычного** процесса, чтобы просмотрщик никогда не работал с правами администратора. Манифест — `asInvoker`.

Папка установки проверяется (`validate_install_dir`): абсолютный локальный путь без `..`, последний элемент — `vibe-md-viewer`, не внутри `%SystemRoot%`, без `" % !`; для всех пользователей — ровно `Program Files\vibe-md-viewer` (иначе родительскую папку мог бы подменить обычный пользователь). Удаление сносит только папку, где есть метка установщика и наш exe (`is_our_install_dir`), а от имени администратора — только прямо в Program Files (`may_delete`).

Повышенная копия копирует **сам запущенный образ**, а не файл по пути (`open_own_image`): имя файла — по отображению образа (`K32GetMappedFileNameW`, следует за переименованиями), файл открывается с запретом записи и удаления для других, идентификатор файла сверяется повторно. Так подменить setup.exe в «Загрузках», пока идёт запрос UAC, нельзя.

| Ситуация при запуске | Что происходит |
| --- | --- |
| Не установлено | Стартовая страница с кнопкой «Установить» (Program Files, UAC; при отказе — предложение установить для себя). |
| Установлена **более старая** версия, запущен новый exe без файла | Сразу вопрос «Обновить X → Y?». Да → (UAC) → `install_files` + `register_at` → запуск обновлённой программы из обычного процесса. |
| Установлена та же/более новая версия | Обычный запуск; на стартовой странице — «Переустановить» / «установлена более новая». |
| Запущены из папки установки | «Сделать программой по умолчанию», «Удалить». Настройки — `%APPDATA%\vibe-md-viewer`. |

Обновление файла: существующий `vibe-md-viewer.exe` переименовывается в `vibe-md-viewer.old.exe` (запущенный exe переименовать можно, удалить — нельзя), новый копируется, старый удаляется сразу или при следующем запуске (`cleanup_old`). При ошибке копирования — откат переименования.

Реестр: ProgID `VibeMdViewer.Markdown` и путь не меняются между версиями, поэтому выбор пользователя «по умолчанию» (UserChoice) остаётся в силе. Чужой обработчик `.md` не перебивается (ставим `OpenWithProgids`, а `(Default)` — только если пусто). Логика реестра одинакова для HKLM и HKCU и проверяется тестом на временной ветке `HKCU\Software\VibeMdViewer-Test-<pid>`, которая удаляется после теста.

Удаление папки с запущенным exe: фоновый `cmd /d /v:off` до 30 секунд пытается удалить папку, пока все копии программы не закроются.

**Переименование vibe-mdViewer → vibe-md-viewer (0.2.0).** `installed()` узнаёт и установку 0.1.x (папка `vibe-mdViewer` с `vibe-md.exe`); её обновление ставит программу в соседнюю папку `vibe-md-viewer` (`Installed::target_dir`). После установки `do_install` убирает записи со старым именем (`Applications\vibe-md.exe`, `RegisteredApplications\vibe-mdViewer`) и ставит в очередь удаление прежней папки — путь берётся из `InstallDir` той же области реестра (для «всех пользователей» это HKLM, куда пишет только администратор), папка удаляется, только если `is_our_install_dir` (имя, метка установщика, exe), до 10 минут — пока старая версия открыта. Ключи `Software\VibeMdViewer`, `Uninstall\VibeMdViewer` и ProgID `VibeMdViewer.Markdown` не менялись (это то же имя в принятом для реестра виде), поэтому выбор «программы по умолчанию» сохраняется. Настройки: при первом запуске установленной 0.2.0 папка `%APPDATA%\vibe-mdViewer` переименовывается в `%APPDATA%\vibe-md-viewer` (`settings::data_dir`). Тесты: `legacy_install_is_recognized_and_moved`, реестровый тест на временной ветке.

## Ограничения текущей версии

- SVG не показываются (будет через безопасный Rust-рендерер resvg).
- Анимированные GIF — первый кадр.
- Mermaid-диаграммы и формулы LaTeX показываются как код (нужен браузерный движок или отдельный рендерер).
- Масштаб для мониторов с разным DPI: приложение «system DPI aware» — на втором мониторе с другим масштабом картинка может быть чуть размыта.
